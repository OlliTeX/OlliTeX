## e2e: SHARING/ACCESS full lifecycle (2-user) — invite email→accept, token links, request-access loop, remove impact

Current: modals-p4 pins invite+remove (green) and the SHARE modal wire; access-request API proven at wire level; clone pinned at API/zotero level. But the CONNECTED end-to-end story is untested:

Legs:
1. **Invite full loop**: owner invites B (File→Share→invite, email captured by smtpsink) → B opens the invitation LINK (from the mail body) → accept UI → project appears in B's project list with the correct role → B edits → owner sees (already collab-pinned) — the missing halves are the mail-link leg and the list/appearance assertions.
2. **Permission change**: owner demotes B owner→editor→commenter (UI) → each step verified by B-side capability: editor can edit (pinned), commenter GETs but POST /message (or doc write) is REJECTED (wire negative), role shown correctly in the share modal (owner-side UI).
3. **Token/share links**: create a read token link (tokenaccess feature, /project/:pid/token or the share-UI leg) → fresh context (incognito) opens the link → reads OK, WRITE is rejected; revoke the token → new attempt 401/403.
4. **Request-access loop**: B (no access) opens project URL → Request access (read-only surface) → owner sees request (UI) → owner grants editor → B's next load has editor access (no re-login; permission propagation) → owner's share modal reflects the membership.
5. **Remove impact**: owner removes B → B's project vanishes from B's list (pinned at UI) AND B's next doc read is rejected (negative wire) — the "impact" legs are the new part.
