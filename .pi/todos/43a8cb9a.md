## Live audit Issue 024 — "sample.bib contains the CONTENT OF main.tex" — ROOT CAUSE FULLY CHAINED (2026-09-30)
### Root cause (code-level, all evidence in-repo)
The Yjs collab design is a SINGLE-DOCUMENT room per PROJECT (D19 hard-cut), while the IDE UI is multi-file:
1. Room = project id, ONE Y.Text — providers.ts `room: collab/{projectId}` (no doc id); collab.go line 7 "room name = project id"; engine.ts createEngine(projectId, sink).
2. Room seed = the project's rootDoc_id doc via docstore — seedsource.go SeedText (no rootDoc_id → empty seed; "Test 2"/frog project has NO rootDoc_id in mongo).
3. EVERY opened file binds the same room — document-container.ts ensureEngine(): createEngine(projectId, sink) — the sink is per-file but the room/Y.Text is project-wide.
4. Consequences (exact audit symptoms):
   - sample.bib view shows the room content (main.tex or stale IndexedDB residue) — "wrong content in file" (024).
   - An edit in sample.bib REPLAYS INTO THE SHARED ROOM → cross-file data corruption risk (007/017/014 cluster: editor vs download vs history mismatch — download reads docstore which holds the ORIGINAL creation content because nothing writes room edits back to the docstore).
   - Per-browser divergence: content also cached in IndexedDB (`ollitex-collab-{pid}`) which merges in and can resurrect stale content.
### Verified facts
- mongo docs collection is CORRECT: main.tex = LaTeX template (118 lines), sample.bib = greenwade93 bib (10 lines). docstore GET per-doc returns correct content for BOTH. Store/sync are intact — the corruption never happened at storage.
- Live editor renders the compiled PDF (canvas) + single project-wide source room; no per-doc room exists.
### Why it is OWNER-GATED (not a unilateral fix)
Proper fix = P3 workstream "multi-document collab": per-(project,doc) rooms, per-doc seeding, per-doc history/review/wordcount contracts (D19/D40 room-name contracts flow through collabhistory, review anchors, wakatime), plus data semantics decision (room vs docstore as source of truth; whether to reset the existing legacy room content which currently holds the only copy of some live edits + IDB invalidation of stale client caches). That is a design + data-repair decision, not a bounded parity bug.
### Recommended plan (for owner)
- Immediate safe guardrail (no data change): non-root docs render their real docstore content read-only with a clear "multi-file editing is P3" notice + IDB cache-name bump so stale client caches stop resurrecting; root doc keeps full collab editing.
- P3: multi-document collab design (rooms per doc, seeds, history key, write-through/migration of docstore).
Related: closes the mechanism behind 007/017/014 content-mismatch cluster (edits live in the shared room; downloads/history read other sources).
