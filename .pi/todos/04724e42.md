## Task (owner request 2026-10-11)
**Check whether the upstream review-Overview completeness bug also affects OUR fork**, and pin it with a repro/regression test if we are immune.

### Upstream report (reference: `/data_1/image_mining/the_diff/review-overview-all-docs`, commits `fe430a0e` + `f1b9809f`)
**What**: the review panel's **Overview tab** only lists comments + tracked changes for docs **currently loaded in document-updater (Redis)**. Comments/changes in any other doc are missing until that file is opened.

**Why**: `useProjectRanges` → `GET /project/:project_id/ranges` → track-changes `TrackChangesController.getAllRanges` → `DocumentUpdaterHandler.getProjectRanges` → document-updater `ProjectManager.getProjectRanges` → **only** `RedisManager.getDocIdsInProject` (loaded docs).

**Repro**: multi-file project; comment in `chapter2.tex`; flush+unload project from document-updater (or restart DU); open project (lands on main.tex); Overview tab → chapter2 comment **missing**; click chapter2.tex → it appears. On most CE installs this hides behind `CONTINUOUS_BACKGROUND_FLUSH` (unset → docs stick in Redis until DU restarts); with it set, or after any restart, the Overview is incomplete every time.

**Upstream fix**: in `getAllRanges`: (1) `DocumentUpdaterHandler.promises.flushProjectToMongo(project_id)` (POST /project/:id/flush — writes loaded docs to docstore without unloading), then (2) `DocstoreManager.promises.getAllRanges(project_id)` — docstore uses `getAllNonDeletedDocs` (deleted docs excluded), mapped to `[{ id, ranges }]` (empty doc → `ranges: {}`, matching the RedisManager._deserializeRanges wire the frontend expects: `item.ranges.changes`). Tradeoff: Overview request now includes a project flush + possibly a docstore unarchive (slower on very large projects). No frontend changes. Verified on a 6.3.0-ext instance before/after, incl. `CONTINUOUS_BACKGROUND_FLUSH=true` long soak.

## Preliminary findings in OUR fork (2026-10-11, first read) — LIKELY IMMUNE, VERIFY
1. **We already retired document-updater** — `go/services/web/features/trackchanges/handlers.go` (D41 note): the DU `/project/:pid/ranges` cache is gone; **reads are docstore-direct**: "the docstore root document's `ranges` field IS the wire the frontend consumes (`{id, ranges:{changes,comments}}`, use-project-ranges.ts)." So our stack has no "loaded-only Redis" leg for this endpoint **if** the docstore holds ALL project docs (not just loaded ones).
2. **Dedicated docstore ranges impl exists**: `go/services/docstore/ranges.go` (+ docstore.go/memstore.go/mongo.go) — the key question: does our `GET /project/:id/ranges` iterate **all non-deleted docs** (like upstream's `getAllNonDeletedDocs`) or only a loaded set?
3. **Frontend consumes the same wire**: `frontend/js/features/review-panel/components/review-panel-overview.tsx` / `review-panel-overview-file.tsx` / `review-panel-current-file.tsx` — same `item.ranges.comments/changes` contract (no frontend change needed if the wire holds).
4. **Write path question**: when a comment is added while a doc is NOT "open", does our stack persist that doc's `ranges` to docstore promptly (YJS → docstore path, historyv1/chunkstore plumbing)? If comments only land in docstore when the doc is loaded+flushed, a variant of the bug could exist even without DU.
