### Proposed legs (write as 2-3 specs, serial mode, single worker)
1. **In-app notification list**: perform an action that should notify (access request on a project you don't own — request-access modal is already proven in the wave), log in as the owner, open the notification surface (header bell / page), assert the entry appears with correct actor + project + relative time; mark-as-read changes state on re-fetch (wire GET the notifications list API — find the route in go/services/web first).
2. **2-user comment mention**: A comments/@mentions B in a shared project (wire POST /message/new-comment or panel UI — review-panel.spec has the exact shapes), B's session shows it (panel realtime or notification entry); notification carries thread + anchor deep-link.
3. **Access-request lifecycle → notification**: request → owner notified; owner accepts (invite-accept UI, wave-pinned) → requester notified + project appears in their list (full loop).
4. **Mail side (smtpsink)**: at least one notification that has an email leg (invitations/access-request email — smtpsink captures; assert subject/recipient/deep link).
5. **Mute/preference interaction**: disable the relevant preference (settings surface, existing spec leg) → repeat trigger → NO notification (negative leg).
