Scope: architecture/infrastructure backbone deficiencies → improvement backlog, then fix the safe ones.

Known/likely candidates to evaluate (white-box, then verify live):

Build process: classic docker build (2MiB log clip hides failures), no shared build cache across the two Dockerfiles, `make images` ordering (texlive base→full chain), builder-image drift (golang:1.27.1 pin), 50+ layer images at 8-9GB, no image GC policy (registry bloat: ollitex/overleaf:* tags from v1..v26, texlive images).
2. Data plane: single-member mongod replset (no true HA), no automated backups (recovery was a manual .bson.gz restore in AG), Postgres for wakapi unbacked-up, no redis persistence for sessions.
3. Network edges: haproxy restart-after-web-recreate fragility (stale DNS), single LB, no TLS cert rotation story, internal 3000/3001/9090 exposure matrix (subnet-only) — audit whether everything is actually subnet-locked.
4. Go services: single web binary hosting all features (blast radius), no per-feature health endpoints beyond liveness, alerting = cron relay (works, but single relay process; no retry queue for failed mail), oometrics scrapes only when prometheus is up.
5. Frontend: 303-entry storybook gate but e2e suite still ad-hoc (see todo B), vendored bundles (tikz 5MB chunks, milkdown) — bundle size budget, no CSP posture documented.
6. Ops: temp verification accounts (uiverif@dev.local etc.) linger in production mongo, /tmp credential files, .env pin traps (WEB_IMAGE), no runbook for the monitoring stack, no on-call escalation path beyond the relay email.
7. Federation: only 2-instance live proof done; no CI for the dance, token store is mongo (scaling path?).
8. TeXLive 2026: first build in progress; seccomp maintenance burden (new syscalls per distro), R/bioinformatics bloat — consider split images (base/full/rl).
