## Task (owner request 2026-10-11)
**Check whether the upstream review-panel "file view 500 when opening a file" bug also affects OUR fork** — same family as the review-Overview item (TODO-04724e42); pin with repro/regression either way.

### Upstream report (reference: `/data_1/image_mining/the_diff/review-file-500-review-panels`, commit `c019046e`)
**What**: in the review panel's **file view**, clicking a file name (even one with only comments) 500s: `onOpenFileChange` → `getDocument(file_id)`; if that file is **not in document-updater's Redis**, DU returns **`{}` — a falsy body without `ok`** (normally DU answers 200 `{ ok: ..., ... }`). `assertResponseOk` (shared/http) treats that as failure → **500 + alert + console error**. Clicking the same file a **second** time works (doc now loaded). The file list comes from a different source (project list + metadata), so files not in Redis are click-able.

**Upstream fix**: `onOpenFileChange` now calls **`ensureProject(project_id)` first** (POST `/project/:id/load` — no-op when already loaded, returns the full project), and only then fetches the document.

**Upstream verification caveat**: covered by `review-panel.test.tsx` (panel + hooks) — but that suite is **skipped in the upstream repo's CI job** (no web test step), so verification = local run only. Our e2e should exercise the real UI→API path.

## Preliminary findings in OUR fork (2026-10-11, first grep)
1. **Different FE generation** — upstream's `onOpenFileChange` name does NOT occur in our tree; our FE open-file surface is `frontend/js/features/ide-react/editor/open-documents.ts` + `editor-manager-context.tsx` (both call `getDocument`), plus the review-panel file-view components (`review-panel-overview-file.tsx`, `review-panel-current-file.tsx`, `deep-link.tsx`).
2. **DU is retired here** (D41, same as the Overview item) — `go/services/web/features/trackchanges/handlers.go` reads docstore-direct; so the upstream "not in Redis → `{}`" mechanism maps to a question about **our docstore**: does a GET document for a doc not yet materialized return a full body (mongo-backed, on-demand load), or can it return **empty/`{}`/missing** (in-memory leg)? `go/services/docstore/memstore.go` is described as an **in-memory TEST store** (docstore.go:158) — confirm it is test-only and the production path is the mongo-backed `mongo.go`.
3. **Our FE fetch failure semantics**: `frontend/js/infrastructure/fetch-json.ts` (the assertResponseOk analog) — which bodies it treats as failure; if an empty-200 from a Go endpoint would trip the same alert/500 path **and** our Go doc GET can return empty for unloaded docs → the bug shape reproduces even without DU.
4. **Go docstore surface**: `go/services/docstore/{docstore.go,handlers.go,mongo.go,memstore.go,ranges.go}` + whatever web route serves a single document (`go/services/web/...` doc/file routes — locate: /project/:id/doc|file equivalents). Exact read path to be mapped in step 1.
